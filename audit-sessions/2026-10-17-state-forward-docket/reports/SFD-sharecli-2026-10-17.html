02 — Intent, mature contract, CVP and MVP

2.1 Identity and mature finish line

sharecli is a single-binary Rust agent runtime / hypervisor for multi-agent hosts. It detects coding agents via process-tree and pattern scan (it does not wrap vendor binaries as the primary path), watches CPU / MEM / Net / FD / IO activity, and under contention coalesces, debounces, and queues redundant tool work (Lock-Wait-Cache) while an optional FUSE layer intercepts IO and a thermal governor gates speculative work. An agent mesh / shared substrate (membership, coordination, fleet registry) sits above; declarative supervise / serve / tray is operator UX.

Beneficiary: the multi-agent host operator — a single human or a small team running 1-50 heterogeneous coding agents (claude, codex, thegent, ghostty shells, custom research tools) on one workstation.

Durable outcome: the operator can install sharecli once, supervise every coding agent on the host, observe aggregate resource pressure, and let sharecli coalesce redundant agent work without per-tool integration.

11 — Fork, rewrite and re-platform analysis

11.1 What is sharecli today (1-paragraph description)

A single-binary Rust agent runtime / hypervisor for multi-agent hosts. It detects coding agents via process-tree and pattern scan (not vendor-wrap), watches CPU / MEM / Net / FD / IO, coalesces redundant tool work via Lock-Wait-Cache, optionally attaches a FUSE layer for meter/forward/shared-read, coordinates agents through a mesh/substrate with a thermal governor, and exposes supervise / serve / tray operator surfaces plus a 6-pub extern "C" fn FFI C-ABI for embedders. Live in CVP-1.0, deferred to MVP-1.0 for FFI embedder use. 486 Rust files, 101,757 LoC, 19 critical-engineering leaves verified, 5 journeys verified, 1 critical engineering leaf pending (= tray-icon fix), 1 critical assurance leaf blocked (= ci / test on main), 1 MVP gate blocked (= no recorded beneficiary session).

13.3 Authority precedence (governance)

When two sources disagree, the precedence is:

  1. **Code** (what is in the repo today) — top authority for behavior
  2. **Audit** (`COMPREHENSIVE_AUDIT_SCORECARD.md`, audit-sessions) — second authority for measured vs intent
  3. **PRD** (mature contract) — third authority for product scope
  4. **ADRs** (architectural decisions) — fourth authority for design intent
  5. **SPEC, FR** (functional requirements) — fifth authority for functional surface
  6. **CHANGELOG, commit messages** — sixth authority for historical record
  7. **Operator's typed signals** — final override (operator always wins on a tie)

When an ADR contradicts the code, code wins (the operator must update the ADR via a documented PR — see PR #935 for the canonical pattern). When an ADR contradicts the PRD, PRD wins (the ADR must be retired or revised).

15.4 Reconciliation pattern (when an ADR contradicts code)

The canonical pattern for reconciling a contradicting ADR is:

  1. Identify the contradiction (this SFD's audit)
  2. Run `cargo metadata` to confirm the code's behavior
  3. Write a PR that updates the ADR to match the code (e.g., PR #935)
  4. The PR is the single source of truth for the new ADR text
  5. Merge; the ADR is now consistent

This pattern was applied for ADR-0007 (PR #935). It is the recommended pattern for any future ADR contradictions.

15.5 What "risk" means in this SFD

  • **Risk** = a future event with a probability and a cost
  • **Blocker** = a current event that prevents a gate from passing
  • **Debt** = a current state that will cost more in the future if not addressed
  • **Contradiction** = a current state where two sources disagree

These four categories are separate. A risk can become a blocker; a debt can become a contradiction. The 20 risks in §15.1 are risk; the 7 blockers in §13.2 are blockers; the 25+ debts in §07.1 are debts; the 15 contradictions in §15.2 are contradictions.

15.6 What we are NOT doing to reduce risk

  • We are NOT adding a plugin system (PRD v1.0: no)
  • We are NOT adding a mobile app (ADR-0001: no)
  • We are NOT adding an MCP server (ADR-0004: no)
  • We are NOT adding Harbor / SWE-bench (PRD: no)
  • We are NOT silently re-scoping any excluded item (would be fraud on the mature contract)

These are explicit no-go decisions. They reduce risk *by refusing to expand scope*; not by adding new code.
